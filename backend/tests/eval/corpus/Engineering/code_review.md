# 代码评审规范

## 一、总则

为通过团队协作提升代码质量，及早发现缺陷与设计问题，促进知识共享，特制定本规范。本规范适用于公司全部研发仓库的合并请求。

代码评审是研发流程的必要环节，任何代码进入主干前都必须经过评审。

## 二、评审范围

下列变更必须经过代码评审：功能开发、缺陷修复、配置变更、数据库结构变更、公共组件修改、依赖版本升级。

下列变更可简化评审流程，但仍需至少一名评审人确认：文档变更、注释修正、不影响逻辑的格式调整、测试数据变更。

紧急修复可以在评审前合并，但应当在合并后一个工作日内补评审并说明紧急事由。紧急修复每季度不超过五次。

## 三、评审人要求

评审人应当是熟悉相关模块的研发人员。评审人的职级原则上不低于提交人。

涉及核心模块（如支付、鉴权、数据同步）的变更，评审人应当包含该模块的负责人。

单次合并请求的评审人数量要求：普通变更至少一名；核心模块变更至少两名；涉及架构调整的变更至少两名且其中一名为架构组成员。

提交人不得评审自己的代码。提交人也不得通过施压或催促的方式要求评审人快速通过。

## 四、合并请求规范

合并请求应当具备清晰的标题与描述。描述应当包含：变更背景与目的、实现方案要点、影响范围、测试方式、上线注意事项。

合并请求的规模应当适中。单次变更的代码行数建议不超过四百行（不含自动生成代码与测试数据）。超过八百行的合并请求，评审人有权要求拆分。

禁止在合并请求中混入无关改动。例如修复缺陷时顺带做的重构，应当拆分为独立的合并请求。

合并请求应当关联对应的需求单或缺陷单编号。

## 五、评审关注点

评审人应当重点检查以下方面：

正确性：逻辑是否满足需求；边界条件是否处理；异常路径是否有覆盖。

可读性：命名是否表意清晰；函数职责是否单一；注释是否解释了"为什么"而非"做了什么"。

可维护性：是否存在重复代码；抽象层次是否合理；是否引入了不必要的耦合。

安全性：是否存在注入风险；权限校验是否完整；敏感数据是否被记录到日志；外部输入是否校验。

性能：是否引入明显的性能退化；数据库查询是否存在全表扫描；循环中是否存在远程调用。

测试：是否补充了对应测试；测试是否覆盖了新增分支。

## 六、评审时限

评审人应当在收到评审请求后一个工作日内给出首次反馈。合并请求的整个评审周期原则上不超过三个工作日。

提交人应当在收到评审意见后两个工作日内响应。超过五个工作日无响应的合并请求，将被标记为待关闭，由提交人确认后关闭或继续。

评审人与提交人对技术方案存在分歧且无法达成一致的，提交架构组裁决。

## 七、评审意见的处理

评审意见分为三类：必须修改、建议修改、仅供讨论。

必须修改的意见，提交人完成修改后应当回复说明并请求重新评审。建议修改的意见，提交人可以选择采纳或者说明不采纳的理由。仅供讨论的意见不需要阻塞合并。

评审人应当对事不对人，使用具体、可执行的表述，避免"这里写得不好"这类笼统评价。

提交人对评审意见有异议的，应当在评论中说明理由，不得直接忽略。

## 八、评审质量

评审人不得走过场式地直接批准。仅回复"看起来不错"而无实质审查的批准，视为无效评审。

研发效能团队定期抽查评审记录，对无效评审的评审人进行提醒。

评审发现的缺陷数量与严重程度，作为评审人技术贡献的参考指标之一。

## 九、附则

本规范由研发效能团队与架构组共同负责解释。本规范与代码分支与提交规范配套执行。
