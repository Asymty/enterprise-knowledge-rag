# 代码分支与提交规范

## 一、总则

为规范研发团队的代码协作方式，保证代码历史清晰可追溯，降低协作冲突，特制定本规范。本规范适用于公司全部研发仓库。

代码管理遵循主干稳定、分支隔离、提交原子、评审必过的原则。

## 二、分支模型

仓库长期存在两条主干分支：main 分支与 develop 分支。

main 分支始终保持可发布状态，任何时刻从 main 分支构建的产物都应当能够上线。develop 分支为日常集成分支，功能开发完成后合并至 develop。

临时分支包括：功能分支 feature/*、缺陷修复分支 fix/*、紧急修复分支 hotfix/*、发布分支 release/*。

功能分支从 develop 切出，命名格式为 feature/需求编号-简要描述，例如 feature/ORD-1234-add-export。

紧急修复分支从 main 切出，命名格式为 hotfix/版本号-简要描述，修复完成后同时合并至 main 与 develop。

## 三、分支生命周期

功能分支的生命周期原则上不超过十个工作日。超过十个工作日未合并的分支，应当评估是否拆分需求。

功能分支合并后应当删除远端分支。长期未更新的分支（超过三十天无提交）将由仓库管理员清理。

发布分支从 develop 切出，用于版本发布前的冻结与回归。发布分支存在期间，develop 分支继续接收下一个版本的功能开发。

## 四、提交规范

提交信息采用约定式提交格式，结构为：类型(范围): 简述。

类型包括：feat 表示新增功能，fix 表示缺陷修复，docs 表示文档变更，refactor 表示重构，perf 表示性能优化，test 表示测试相关，chore 表示构建或工具变更。

简述使用中文或英文均可，但同一仓库应当保持一致。简述不超过五十个字符，不以句号结尾。

示例：feat(order): 支持订单批量导出；fix(auth): 修复令牌刷新失败的问题。

提交应当保持原子性，一次提交只做一件事。禁止将无关的格式化改动与功能改动混在同一次提交中。

禁止使用"update"、"fix bug"、"修改"等无信息量的提交信息。

## 五、提交前检查

提交前应当执行本地检查：代码能够编译通过；单元测试全部通过；代码格式化工具已执行；无调试代码残留（如打印语句、调试断点）。

禁止提交的内容：编译产物、依赖目录、本地配置文件、密钥与证书、大体积二进制文件。

提交历史中误入敏感信息的，应当立即报告并执行历史清理，不能仅在新提交中删除。

## 六、合并要求

功能分支合并至 develop 前必须满足：代码评审通过且至少一名评审人同意；持续集成流水线全部通过；分支与目标分支的冲突已解决；提交历史已整理（必要时使用变基）。

合并方式统一使用压缩合并（squash merge），保持 develop 分支历史为线性。

禁止直接向 main 分支推送提交。main 分支应当开启分支保护。

## 七、标签与版本

版本发布时在 main 分支上打标签，标签格式为 v主版本号.次版本号.修订号。

主版本号在存在不兼容变更时递增；次版本号在新增向后兼容功能时递增；修订号在向后兼容的缺陷修复时递增。

标签一经发布不得移动或删除。发现发布错误的，应当发布新的修订版本。

## 八、冲突处理

发生代码冲突时，应当由分支作者负责解决，不得随意选择"全部接受我方"或"全部接受对方"。

冲突解决后应当重新运行测试，确认功能未受影响。

涉及公共组件或接口变更的冲突，应当邀请相关模块负责人共同确认。

## 九、附则

本规范由研发效能团队负责解释。各仓库可在本规范基础上制定更细化的规则，但不得低于本规范的要求。
